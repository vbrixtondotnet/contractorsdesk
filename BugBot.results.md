Reviewed the uncommitted duplicate-line-item changes (SQL, C# services, Proposal + Revised Estimates JS) and ran a small dedupe simulation. Findings below, highest severity first.

| Page Name | Bug Description | Severity | Suggested Fix |
|---|---|---|---|
| Revised Estimates / Budget-to-Actual | `spEnsureUniqueProposalLines` deletes duplicate `ProposalLines` by parent + name, but does not reassign `EstimateMappings` (or schedule mappings) from the deleted line’s `EstimateCategoryId` to the kept line. Costs can vanish or attach to an orphaned category. Runs on every ETA load. | High | Before deleting losers: move mappings to the surviving `EstimateCategoryId`, then delete. Or delete only unmapped duplicates. |
| Revised Estimates / Budget-to-Actual | After the new parent+name uniqueness rule, `spCleanUpDuplicateProposalLinesAndEstimateCategories` still partitions duplicates by **Name only**. Same item name under different parents (e.g. Materials > Labor and Framing > Labor) can be treated as duplicates; the unmapped one is deleted incorrectly. | High | Update cleanup to partition by `ParentEstimateCategoryId` + trimmed name (same key as the new uniqueness rule). |
| Proposal | Frontend `#deduplicateLineItemsByName` keeps the higher amount and drops the other; totals can shrink with no warning (e.g. 100 + 250 → 250). Backend `DeduplicateLineItemsByName` does the same on save/load. | Medium | Warn before collapsing, or sum amounts when merging; at least show a toast when rows are removed. |
| Revised Estimates / Budget-to-Actual | Client `#deduplicateLineItemsByName` sums `costToDate` but does **not** recalc `balance` / `percentage`. Simulation: Drywall 1000/200 + drywall 500/300 → costToDate 500 but balance stays 800 (should be 500) and % stays 20 (should be 50). | Medium | After merge, set `balance = revised - costToDate` and recompute percentage (match `EstimateService`). |
| Proposal | Backend `DeduplicateLineItemsByName` drops whitespace-only names; UI still keeps blank rows by `id`. Save can remove placeholder/in-progress rows without a clear error (required-name validation only checks empty string on visible inputs). | Medium | Keep blank names out of silent drop, or block save with an explicit “Item Name is required” and don’t strip them server-side without feedback. |
| Proposal (API after save) | `EnsureUniqueProposalLinesAsync` runs raw SQL `DELETE` after `SaveChanges`, then `GetProposalAsync` loads via a tracked context that still holds deleted `ProposalLines`. Response can show stale/ghost lines until the scope ends. | Medium | Call `ChangeTracker.Clear()` (or detach/`AsNoTracking` reload) after the proc, before `GetProposalAsync`. |
| Revised Estimates (map account) | `pl.Name.Trim()` / `selectedCategory.Name.Trim()` throw if `Name` is null → mapping save can 500. | Medium | Use null-safe compare: `(pl.Name ?? "").Trim().ToLower()` (same pattern already used elsewhere). |
| Revised Estimates (map account) | If a same-name line already exists under the parent, code skips creating a proposal line and never applies `mapping.Amount` to the existing line. Mapping is saved; amount from the new category flow is ignored. | Low | When reusing `existingLineWithSameName`, update its amount (or document that amount is ignored and clear it in the UI). |
